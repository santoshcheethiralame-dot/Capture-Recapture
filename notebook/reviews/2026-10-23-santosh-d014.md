## Verdict: approve D-014 as written

The rule is right, and fixing it before any pilot is the right process.

- **k = 10 matches what the auditor sees.** The tool shows 10 features by
  default, so "in the top 10 on most prompts" means "takes a display slot
  on most prompts". That is the harm the filter removes.
- **The 50% cutoff is conservative, and sharp enough at 100 prompts.**
  Chance that a feature is blocklisted, given its true top-10 share
  (binomial):

  | true share | 0.40 | 0.45 | 0.50 | 0.55 | 0.60 |
  |---|---|---|---|---|---|
  | P(blocklisted) | 0.02 | 0.14 | 0.46 | 0.82 | 0.97 |

  Only features near 0.45–0.55 depend on the prompt sample. #1041 (top-1 on
  19 of 20 check prompts) is far above that. A lower cutoff (say 25%) would
  hide more features that are merely frequent, which raises the risk you
  name, so I would not lower it.
- **Computing it on Gemma-2-2B-it, not per organism, is a strength.** A
  feature that an implant makes fire on every prompt is *not* on the
  blocklist, so it stays visible. Only features already constant in the
  shared base are hidden.
- **Keeping "most changed vs base" unfiltered** covers the remaining risk
  (an implant expressed through a feature the base already fires on
  everywhere): such a feature changes, so it shows up there.

## Code: no defects found

- `top_features` drops blocklisted features *before* taking k, so the
  auditor still gets 10 features.
- `background_blocklist` uses the same token rule and per-prompt maximum
  as the tool. The strict `>` means a feature needs 51 of 100 prompts.
- The prompt bank caches activations before filtering, so changing the
  blocklist never needs a new bank.
- The `mode` bank key keeps old-rule banks from being reused.
- The sentinel-based user span and the offset overlap test in `hf_resid`
  look correct. Thanks also for the double-BOS and eager-attention fixes,
  which were real bugs in my tool.

## Suggestions (not blocking; your call, fix before E09-R004 if you agree)

1. **Pre-specify a risk diagnostic for E09-R004.** This measures the risk
   you name rather than assuming it away. For each pilot organism, report
   (descriptive, not a criterion):
   - (a) any blocklisted feature in that organism's most-changed top 10 on
     more than half of its trigger prompts;
   - (b) any blocklisted feature whose Neuronpedia label matches the
     implanted behaviour.
   Either means the blocklist hid part of the implant from the top-features
   list.
2. **Tell the auditor that background features are hidden.** One line in
   `render()`, e.g. "N always-on background features are hidden from this
   list", so a T3 auditor isn't misled about what the list is. It changes
   presentation only, not the rule or E09-R010. If you agree, I'll add it in
   my next PR (it's my code), or you can.
3. **Record near-threshold features.** In E09-R010's summary, list the
   features with a top-10 share between 0.35 and 0.65 (`top30_by_share`
   nearly covers this already), so the sensitivity is visible if a reviewer
   asks.
